# 抖音互关 / 粉丝追踪

[![CI](https://github.com/nigemagua10/douyin-huguan-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/nigemagua10/douyin-huguan-tracker/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

读取自己的抖音关注列表和粉丝列表，存成 Excel，并和上一次采集对比，
**告诉你谁取关了你**。

**不想登录抖音，先看看效果？** 一条命令用虚构数据跑出完整报表：

```bash
python -m pip install -r requirements.txt
python src/main.py --demo
```

结果在 `demo/output/`，包含「取关了我」「新粉丝」等全部工作表，
用的是一份**完全虚构**的数据，不会读取或修改你的任何真实数据。

**想用自己的数据？** 最短路径：

```bash
git clone https://github.com/nigemagua10/douyin-huguan-tracker.git
cd douyin-huguan-tracker
python -m pip install -r requirements.txt
# 按「使用 → 第一步」采集 JSON，放进 data/raw/
python src/main.py
```

第一次运行只建立基线，第二次开始才会出现「取关了我 / 新粉丝」。

## 它是怎么拿到数据的

抖音网页版的接口现在要带 `a_bogus` + `x-secsdk-web-signature` 三件套签名
（JSVMP 混淆），纯 HTTP 复刻既脆弱又是绕过反爬。

所以本项目换了个思路：**用你自己浏览器里已经登录的会话，把页面自己发出的请求
响应录下来**。页面本来就会带着合法签名去拉关注/粉丝列表，脚本只是把这些响应对
下来并归档 —— 不构造请求、不伪造签名。

代价是采集时要手动点一下；好处是签名怎么改都不影响你。

## 使用

### 第一步：采集

1. 浏览器（Chrome / Edge / Comet 等 Chromium 浏览器）登录 `www.douyin.com`
2. 打开**你自己的主页**，切到「关注」标签：
   `https://www.douyin.com/user/self?showTab=following`
3. **用「代码片段」运行脚本**（`F12` 后）：
   1. 点顶部 **「源代码」**（Sources）
   2. 左侧栏找 **「代码片段」**（Snippets）——找不到就点 `»` 展开
   3. 点 **「+ 新建代码片段」**，命名随意
   4. 在右边编辑区 `Ctrl+V` 粘贴
      [`collector/douyin_collector.js`](collector/douyin_collector.js) 的全部内容
   5. `Ctrl+Enter` 运行
4. 右下角出现面板后，让它**自动小步滚动**「关注」列表
   （**不要手动一下拖到底**：虚拟列表会跳过中间页，顺序会乱）
5. 面板显示「已到底」后，切到「粉丝」标签，同样等它滚到底
6. 点面板上的 **【下载 JSON】**，把文件放进本项目的 `data/raw/` 目录

> **为什么用代码片段而不是 Console？** 浏览器的 Self-XSS 保护会拦截往 Console
> 里粘贴多行代码，要先手动输入解锁口令（英文版 `allow pasting`，**中文版
> `允许粘贴`**），而 Edge 中文版这个提示有翻译 bug，有时只显示 `{PH1}` 占位符。
> 代码片段编辑器**完全不触发粘贴拦截**，省掉这一步。
>
> ⚠️ **`F5` 刷新后脚本就没了，需要重新 `Ctrl+Enter` 运行一次**（代码片段本身会保留）。

**面板怎么看**：关注/粉丝各显示「采到人数 / 接口报总数」，以及分页状态：

| 分页状态 | 含义 |
|---|---|
| `已到底` | 接口报告没有更多了，列表已拉完 |
| `还有更多` | 接口说还有下一页，继续往下滚 |
| `?未知` | 还没收到过带分页信息的响应 |
| `原始 N 条` | 去重前的总条数；比采到的人数大是正常的（同一页会被重复请求） |

> 粉丝那一行如果出现「其中 N 个被接口标为风险/隐藏」，那是接口自己报的
> `sink_risk_uids`：这些账号**计入总数，但接口不返回昵称、抖音号、资料**，
> 列表里也不会出现。它们不是采集器漏抓；其中属于互关的人，生成报表时会
> 用关注列表的 `follow_status=2` 补回「我的粉丝」表。

可选的控制台命令（**必须在脚本运行之后才有效**）：

| 命令 | 作用 |
|---|---|
| `__dyStatus()` | 查看当前采集到多少 |
| `__dyDump()` | 手动触发下载 |
| `__dyStop()` | 停止自动滚动 |
| `__dyReset()` | 清空已采集数据 |
| `__dyUnknown()` | 查看没认出来的用户列表接口（路径改版时反馈用） |

> 如果面板出现 **「未识别接口 N 个」**，说明抖音又换了列表接口路径；
> 控制台运行 `__dyUnknown()`，把里面的 `path` / `keys` 反馈到 issue 即可。

> 数据会暂存在浏览器 localStorage 里，同一天内刷新页面不会丢。
> 脚本改了去重逻辑之类会影响数据正确性的地方时，会提升存储版本号，
> **旧版本缓存会在加载时自动丢弃**，不需要手动清理。
> 如果自动滚动没生效，手动往下滚也一样会被记录。

### 第二步：生成报表

```bash
python src/main.py
```

或者双击 [`run.bat`](run.bat)。生成 `output/抖音好友关注_YYYY-MM-DD.xlsx`。

常用参数：

```bash

python src/main.py --reset           # 清空历史，本次重新建立基线
python src/main.py --raw-dir 别的目录
```

**第一次运行只建立基线**，从第二次开始才会显示「谁取关了你」。

## 工作表说明

| 工作表 | 内容 |
|---|---|
| **互关好友** | 你关注了、对方也关注了你的人 |
| **我的粉丝** | 所有粉丝（粉丝接口 + 从关注列表补入的互关；补入的排在末尾） |
| **我的关注** | 你关注的所有人 |
| **取关了我** | ⚠️ 曾经关注你、现在不关注了 —— 按日期倒序的流水账 |
| **新粉丝** | 首次出现的新粉丝 |
| **我取关了** | 你取关过的人 |
| **历史概览** | 每次采集的关注数/粉丝数/互关数 + 各项变化数 |
| **提示** | 本次运行的异常说明（比如没采到粉丝数据） |

前三张表的列：**序号 · 备注 · 昵称 · 抖音号 · 关系 · 账号注册时间 · 粉丝数 · 关注数 · 作品数 · 认证 · 简介**，
「抖音号」是可点击的主页链接。

### 怎么排序又不丢原始顺序

每张表首列都有一个**固定的序号**，代表这张表原本的时间顺序。

比如你想按粉丝数从多到少看一眼：

1. 选中表头 → **数据 → 筛选**（表头本来就已经开了筛选，直接点「粉丝数」列的筛选按钮选「降序」）
2. 看完了想恢复 → 点「**序号**」列筛选按钮选「**升序**」

就回到按关注时间排的原始顺序了，**不用撤销**，也不用重新生成报表。

> 序号是生成时就写死的数值，不随排序变化；排序只是改变行的显示位置。
> 同样的道理，「取关了我」「新粉丝」这些流水表也能随时按粉丝数排、再按序号排回来。

**「关系」列怎么来的？** 不靠两个列表求交集，而是直接用抖音自己在列表里标的
`follow_status` 字段：

| 字段值 | 出现位置 | 含义 |
|---|---|---|
| `2` | 两个列表 | **互关** |
| `1` | 关注列表 | 我单向关注对方 |
| `0` | 粉丝列表 | 对方单向关注我 |

**为什么不能靠求交集？** 粉丝列表因为已注销账号等原因会少人，其中一部分其实
和你互关。求交集会把这批人误判成「单向关注」—— 会少算一批互关。
`follow_status` 不受列表完整性影响。

**排序**：「互关好友」「我的关注」按关注时间排，**默认最早关注的在最上面**。
「我的粉丝」按粉丝列表自己的顺序排；从关注列表补入的互关排在末尾（按关注顺序）。

```bash
python src/main.py                  # 最早关注的在最上面（默认）
python src/main.py --sort recent    # 改成最近关注的在最上面
```

排序依据是**接口自己的分页位置**，不靠猜。抖音这个接口前后换过三种分页方式，
程序按可靠性依次尝试（运行时会在控制台打印实际用了哪种）：

| 依据 | 时期 | 说明 |
|---|---|---|
| **`offset`** | 2026-09 起 | 优先用**请求**里的 offset（采集器记成 `req_offset`）；旧数据退回响应里的 `offset - 本页条数`。只有每一页都有位置、从 0 开始且随页号不递减时才采用 |
| `max_time` / `min_time` | 更早 | 时间游标；只有在**每一批**都带游标时才采用 |
| **混合分页** | 近期实测 | 前几页只有 offset（列表顶部），后面的页只有时间游标（从列表底部往上加载）。两段分别排序后拼接 |
| 数组顺序 | 兜底 | 上面三种都不可用时；用户中途才滚动、或来回翻了两遍时会乱，出现这种情况会给出警告 |

> 近期实测抖音把响应里的 `offset` 有些批次恒置 0；后来又出现
> 「offset 页 + 时间游标页」混在同一次采集里的情况。程序按
> 完整 offset → 全部时间游标 → 混合分页 → 数组顺序 依次尝试，
> 控制台和「提示」页都会写明这次实际用了哪种依据。
>
> `--sort` 只控制显示方向（最早 / 最近在前）；顺序本身的可靠性看「提示」页
> 写的依据。如果写的是「数组顺序」，说明分页信息不够，建议按提示重新采集。

> ⚠️ 抖音**不返回每个人的关注时间**（102 个字段里都没有），所以「某人具体哪天
> 关注的」拿不到。但**排序依据是可考证的** —— 用接口返回的分页位置还原，与你怎么
> 滚动、翻了几遍无关；只有分页位置本身不可用时才会退回数组顺序并给出警告。
>
> 接口通常按「最近关注 → 最早关注」返回；程序会从翻页日志判断实际方向，
> `--sort earliest` 倒过来、`--sort recent` 保持原样。

**「账号注册时间」**来自接口的 `create_time`，是**对方账号的注册日期**，
不是你和他的关注时间——这两件事容易混。

**表格样式**：所有格子加粗、水平居中（表头白字），只有**「简介」列靠左**——
多行文本居中反而不好读。

**抖音号的「数字以文本形式存储」警告已自动忽略。** 有些抖音号是纯数字
（如 `1564072609`），但它本质是 ID 不是数值，只能按文本存，Excel 会在每个这种
格子上画绿色小三角。报表里已经写入了忽略规则（等价于右键「忽略错误」），
不用手动一个个点。

**「简介」列会自动折行**，并**保留原文里的换行**。抖音的个性签名本身是带分行的
（有的还用连续换行做空行），这些是作者排版的一部分，会被原样保留；
行高按内容自动撑开，不会被截断。

「取关了我」这类流水表是**累积**的 —— 三个月前取关你的人也会留在表里，
不用担心错过。

## 常见问题

### 为什么「我的粉丝」比主页显示的粉丝数少？

**这是抖音的官方行为，不是工具丢数据。**

抖音明确说明：**已注销、被封禁的账号，以及被平台清理的虚假粉丝/僵尸粉，
仍然计入粉丝总数，但不会出现在粉丝列表里**。所以「显示的粉丝数」永远 ≥
「列表里能看到的人数」。

怎么确认工具没丢数据？看三个信号：

1. **面板上粉丝那一行是不是 `已到底`**。是的话说明接口报告"没有更多了"，
   页面已经翻到底，不是滚动停早了。若是 `还有更多`，那才是没拉完，继续滚。
2. **关注列表是否精确匹配**。关注和粉丝走的是同一套采集与去重管线，
   如果关注数能和接口报的总数一丝不差地对上，就说明管线本身是可靠的。
3. **接口有没有 `sink_risk_uids`**。粉丝列表响应里的 `store_page.sink_risk_uids`
   会明确列出被隐藏的账号 UID；报表「提示」页会把「总数 − 可枚举数」和它对账。

报表会做两件事：

- **先补互关**：粉丝接口偶尔会漏掉一部分互关；报表用关注列表的
  `follow_status=2` 把它们补回「我的粉丝」表末尾（这些人在关注列表里有完整资料）。
- **再报差额**：补完后仍然差的，是接口只返回 UID、不给资料的单向粉丝。
  「提示」页会把「接口总数 − 可枚举数 = 风险/隐藏账号数」对账写清楚。

> **互关好友不会受影响。** 「互关好友」表直接用关注列表的 `follow_status=2`，
> 不依赖粉丝列表，所以互关是完整的。粉丝表少的主要是单向粉丝。

### 采集面板上的人数是 0，或者一直不涨

- 确认停在**你自己的主页**，且已经切到「关注」或「粉丝」标签
- 确认列表在页面上**真的渲染出来了**（能看到头像和昵称）
- 采集器现在匹配任何带 `following` / `follower` + `list` 的接口，不再死守
  `/user/following/list/` 这一种路径
- 如果面板出现 **「未识别接口 N 个」**，控制台运行 `__dyUnknown()`，把里面的
  `path` 和 `keys` 发到 issue —— 那说明抖音又换接口路径了
- 还不行就跑 [`collector/douyin_diagnose.js`](collector/douyin_diagnose.js)，
  它会打印 following/fans 的真实返回结构，并把**未识别的用户列表接口**也打出来

### `__dyReset()` 之类的命令报红

这些是**脚本运行之后才存在的函数**，单独粘贴执行必然是
`is not a function`。先运行采集脚本，再用这些命令。

## 备注怎么维护

备注可以**直接写在 Excel 的「备注」列里**，下次运行会自动回收，不会丢。

- 同一个人出现在多个表里，随便在哪个表里填都行（回收时取并集，非空值优先）
- `remarks.csv` 是脚本维护的备份，已有的值优先级最高，可以用来批量导入
- 要**彻底删掉**某人的备注，删掉 `remarks.csv` 里对应的行最干净

## 已知限制

- **粉丝数永远 ≥ 能枚举到的粉丝数。** 抖音把已注销、被封禁、被平台清理的
  虚假粉丝计入总数，却不放进列表。**网页接口只通过 `store_page.sink_risk_uids`
  返回这些账号的 UID，不返回昵称/抖音号/资料**。其中互关可以用关注列表补回来；
  单向粉丝在网页端补不回来（手机 App 能看到）。
- **拿不到每个人的具体关注时间。** 接口不返回该字段（102 个字段里都没有），
  只在翻页游标里给出每页的时间边界。所以**排序是准确的**，但「某人具体哪天
  关注的」无法得知。
- **排序精确到页内。** 翻页游标给出每页的时间边界，所以「页与页之间」的先后
  是确定的；同一页 20 个人内部依靠接口返回顺序，这一层没有独立的时间戳可校验。
